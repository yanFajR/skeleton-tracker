# Project Status

- Authentication: a single-user login page protects every page, video route, and API endpoint. The default account is `admin` / `AdminAman123` and can be overridden with `MOTION_TRACKER_USERNAME` and `MOTION_TRACKER_PASSWORD` (or `MOTION_TRACKER_PASSWORD_HASH`). Passwords are salted PBKDF2-HMAC-SHA256 digests compared in constant time; sessions use an HMAC-signed `HttpOnly`, `SameSite=Lax` cookie valid for eight hours, with the signing secret persisted in `data/.auth_secret` or supplied through `MOTION_TRACKER_SECRET_KEY`. Five failed logins per minute trigger a temporary lockout, unauthenticated API calls return 401, and login redirect targets are restricted to same-site paths. The app uses no SQL database (metadata is JSON), so SQL injection is not applicable; identifiers and filenames remain validated before use.

- Current product phase: B4 elbow-angle analysis, B5 result playback review, and B6 responsive review UI are implemented. The UI remains a single-session workflow.
- B4: elbow-angle analysis is implemented. MediaPipe pose inference calculates left and right elbow angles from shoulder-elbow-wrist landmarks in the same frame used for the skeleton overlay. Frame angle metadata is shown while scrubbing legacy and session result videos; unavailable, low-confidence, zero-length, or incomplete landmarks are displayed as unavailable rather than 0 degrees.
- Trunk measurement: per-frame trunk lean is calculated from the midpoint of both shoulders and both hips as the angle of the shoulder midpoint from the vertical hip axis. Low-confidence or incomplete shoulder/hip landmarks are shown as unavailable. This is a 2D camera-dependent lean measurement and does not automatically classify backward or forward lean.
- B5/B6: session result review now provides play/pause, backward/forward frame navigation, playback speeds 0.1×, 0.25×, 0.5×, 0.75×, and 1×, synchronized frame-angle display, responsive controls, and video-loading/playback errors.

- Legacy workflow: the legacy baseline/retake UI has been removed. Backend comparison endpoints, metadata, and historical data remain intact for compatibility; no files or records are deleted.
- New session workflow: `/api/sessions` creates a single-session record only. The web page previews the source video, displays its duration, and offers start/end time and range controls. Selecting **Gunakan Video Ini** saves a new MP4, updates the session's trim metadata, then runs the existing pose pipeline against the trimmed file. Session pose requests return HTTP 409 until a successful trim exists; pose analysis never falls back to the source video.
- Trimming: `video_trimmer.py` uses the `imageio-ffmpeg` binary already installed in `.venv`. It probes source and output video, encodes H.264/yuv420p MP4, applies a five-minute timeout, and cleans up incomplete generated output. The original source is neither overwritten nor deleted.
- Metadata: `data/sessions.json` stores trimming source/output filenames, selected times, source/trimmed durations, timestamp, status, and a failure message when applicable. The trim `status` and `trimmed_duration` are authoritative; redundant `enabled` and `duration_seconds` fields are not written. Trim output ownership is associated with its session, and only the successful trimmed file is passed to pose analysis.
- Metadata ownership: `POST /api/videos/{filename}/pose` now resolves the owner of a file from both stores before processing. If the file is present in both, the API returns a clear 409 conflict instead of silently choosing one store. If the file is absent in both stores, it returns 404.
- Restoration and status: comparison pages remain addressable with `?comparison_id=<id>`; the new session records are also addressable by `session_id`. Uploaded attempts are started automatically, active processing is polled, and failed attempts show an error and can be retried when available. Missing files are handled through reconciliation in both stores.
- API: `POST /api/sessions/{session_id}/trim` trims an existing session without creating a session or comparison. `GET /videos/{filename}` serves source and trimmed previews using validated UUID filenames. `POST /api/videos/{filename}/pose` rejects untrimmed sessions with HTTP 409 and uses only the successful trimmed file while preserving legacy comparison processing.
- Storage: comparison records and generated filenames remain stored in `data/comparisons.json`; session records are stored in `data/sessions.json`. Both stores are atomic and local to the current single-process app; no historical comparison data is deleted.
- Validation: session IDs are validated; clients cannot provide a filename or path to the trimming endpoint. Start must be non-negative, end must be later than start and within the probed source duration, and selection duration must be from 0.5 to the configured analysis maximum (120 seconds by default). These limits are configurable through `MOTION_TRACKER_MIN_TRIM_DURATION_SECONDS` and `MOTION_TRACKER_MAX_VIDEO_DURATION_SECONDS`.

- B2.1 fixtures: `tests/conftest.py` generates CFR 30/60 FPS, VFR, portrait, landscape, rotation-metadata, and nonstandard-rate/duration MP4s using the `imageio-ffmpeg` binary already installed in `.venv`. - B2.2 probing: `video_trimmer.py` uses bundled FFmpeg `showinfo` with `-noautorotate`. `frame_count` counts all decoded frame records, including frames without PTS; `valid_pts_count` is separate. Incomplete PTS blocks average-FPS/CFR conclusions and fails timing validation. `nominal_frame_rate` and its rational numerator/denominator are populated only for CFR streams whose `showinfo` frame_rate agrees with complete CFR PTS; they stay null for VFR. `inferred_cfr_frame_rate` is a distinct calculated reciprocal-median-PTS estimate. `actual_output_frame_rate` is populated only for a trimmed CFR stream. Average FPS is calculated from complete valid PTS.
- B2.2 integration: after trimming, source and output streams are probed, technical fields and provenance are merged into the owning session's trim metadata, and duration/timestamp/frame count/resolution/rotation/codec/pixel format/orientation are validated. - B2.2 timing remediation: timestamp duration uses the last frame's `duration_time` when available; otherwise the final interval is estimated from the median positive PTS interval and its provenance is marked `estimated`. Container/timestamp comparison uses 10 ms for FFmpeg's centisecond duration text, expanded to one average frame interval plus 5 ms only when the last frame duration is estimated. Requested trim duration allows at most one frame interval plus 5 ms, not the former fixed 100 ms/two-frame floor.
